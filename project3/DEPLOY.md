# Deploying TaskFlow

Task 1 committed to "deploy on a live server with SSL/HTTPS". This is how the
app gets there. One Render web service hosts both halves: the build compiles
the React client, and the Express server serves `client/dist` next to `/api`.
That keeps the auth cookie same-origin, and Render terminates TLS so the site
is HTTPS — which the service worker also requires to register.

The blueprint is [`render.yaml`](../render.yaml) in the repository root (Render
only reads blueprints from the root).

## 1. Database — MongoDB Atlas

1. Create a free M0 cluster at <https://cloud.mongodb.com>.
2. **Database Access** → add a user with a password. Keep both.
3. **Network Access** → add `0.0.0.0/0`. Render's free plan has no fixed
   outbound IP, so the cluster has to accept any address; the database user's
   password is what protects it.
4. **Connect** → *Drivers* → copy the connection string and append the database
   name:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/taskflow?retryWrites=true&w=majority
   ```

   URL-encode the password if it contains `@ : / ? # [ ] %`.

## 2. Service — Render

1. Push this repository to GitHub.
2. Render dashboard → **New** → **Blueprint** → pick the repository. Render
   reads `render.yaml` and proposes the `taskflow` service.
3. It asks for the two `sync: false` values:
   - `MONGO_URI` — the Atlas string from step 1
   - `CLIENT_ORIGIN` — leave the placeholder for now, fixed in step 4
4. Apply. `JWT_SECRET` and `SESSION_SECRET` are generated by Render, so no
   secret is ever written into the repository.

Without a blueprint, the same service can be created by hand: **New → Web
Service**, root directory `project3`, runtime Node, and

```bash
npm --prefix client ci && npm --prefix client run build && npm --prefix server ci --omit=dev
```

```bash
npm --prefix server start
```

with health check path `/api/health` and the six environment variables set
manually.

## 3. Environment variables

| Key | Value | Notes |
|---|---|---|
| `NODE_ENV` | `production` | Serves `client/dist` and marks cookies `secure` |
| `NODE_VERSION` | `22` | |
| `MONGO_URI` | Atlas connection string | Secret |
| `JWT_SECRET` | generated by Render | Secret; the server refuses to boot without it in production |
| `SESSION_SECRET` | generated by Render | Secret |
| `CLIENT_ORIGIN` | `https://<service>.onrender.com` | CORS allow-list; same-origin in production, so it only matters if the client is ever hosted separately |
| `PORT` | injected by Render | Do not set |

## 4. After the first deploy

1. Copy the live URL (`https://taskflow-xxxx.onrender.com`).
2. Set `CLIENT_ORIGIN` to exactly that URL — no trailing slash — and redeploy.
3. Verify:

   ```bash
   curl -i https://<service>.onrender.com/api/health      # {"status":"ok"}
   curl -i https://<service>.onrender.com/api/tasks       # 401 without a cookie
   ```

   In the browser, on the live URL:
   - sign up, log out, log back in — the session survives a refresh
   - `document.cookie` in the console is empty (the JWT is HTTP-only)
   - the response cookie carries `Secure` (DevTools → Application → Cookies)
   - DevTools → Application → Service Workers shows `sw.js` activated, and
     Manifest lists three icons with an install prompt available
   - add / edit / toggle / delete a task, then check Atlas → Collections for
     the `users`, `tasks`, and `sessions` documents

## Notes

- The free plan sleeps after ~15 minutes idle, so the first request afterwards
  takes 30–60 seconds. Worth knowing before a live demo.
- Deploys are triggered by pushes to the tracked branch.
- If the build fails on `npm ci`, the lock file is out of step with
  `package.json` — run `npm install` locally in that folder and commit the
  updated `package-lock.json`.
- Railway works the same way: root directory `project3`, identical build and
  start commands, same environment variables.
